# 开发与审查流程

[文档索引](../README.md) · [验收矩阵](ACCEPTANCE.md) · [路线图](ROADMAP.md)

可用命令以 [package.json](../package.json) 与 [README](../README.md) 为准；运行数据、缓存与原始日志使用隔离目录，不进入源码提交。

## 工作单与职责

每个问题有一个明确负责人，负责收敛范围、更新状态和接收审查结果。需求整理、实现与验收、独立审查分开；独立审查由未主导该实现的人或独立执行者承担。自查不能标记为已独立审查。并行修改使用隔离工作区并明确文件所有权，集成由负责人协调，避免共享目录混入彼此变更。

工作单至少写明：问题与用户路径、范围、负责人、涉及契约、可证伪验收项、平台与失败条件、验证计划、未决决策。纯文档任务也要明确事实来源和不得夸大的状态。

## 从验收到交付

1. **先定义验收。** 从 [ACCEPTANCE](ACCEPTANCE.md) 选受影响项，补充触发条件、可观察结果、反例与真实平台要求。
2. **先建立失败证据。** 修复先用测试重现问题；新能力先建立能够因缺少能力而失败的契约测试或最小实验。测试应断言对外行为，不能只复述实现。
3. **实现最小变更。** 修改前阅读相关子系统文档和实际调用路径；保持内核与业务边界，记录必要的通用契约演进。
4. **运行回归与用户路径。** 检查依赖方、失败分支、停用清理和状态恢复。单元测试、浏览器验证、原生窗口及打包产物的证据分别记录。
5. **独立审查。** 审查者核对需求、边界、真实执行路径与版本证据，给出可定位的问题及严重程度；每个问题仍由单一负责人处理。
6. **必要时精简。** 删除无实际路径支撑的抽象、重复状态、临时分支与调试残留，避免为未来猜测增加结构。精简改变行为或实现后重新运行相关验证。
7. **关闭工作单。** 相关测试与验收通过、审查问题处理完毕或明确阻塞后，更新子系统文档、[HANDOFF](../HANDOFF.md) 与有证据的新 [LESSONS](../LESSONS.md)。未验证项保留未验证状态。

纯文档和低影响可逆变更使用静态检查及文档审查，无需为其编造运行测试、安装依赖或启动服务。严重问题按影响立即处理，不等待累计出现三次。

## 子系统文档最小内容

子系统出现真实实现时，其文档应贴近代码维护；目前不创建假定存在的子系统说明。每份文档应说明：

| 项目 | 需要回答的问题 |
| --- | --- |
| 所有权与边界 | 谁负责哪些状态、资源与副作用？上下游依赖哪些公共契约？ |
| 契约与状态转移 | 何时可用、何时失效？兼容、取消、停用、升级如何表达？ |
| 失败行为 | 部分成功、超时、拒绝授权、依赖缺失、读取失败和恢复分别如何处理？ |
| 真实路径 | 用户操作如何经过 UI、扩展、宿主和原生层得到结果？源码入口在哪里？ |
| 验证与限制 | 哪些命令或操作验证哪些保证？哪些平台和路径尚未覆盖？ |

## 证据与失效

使用[验收证据记录](ACCEPTANCE.md#证据记录要求)的统一格式，以 Git 提交、工作区差异及必要的未跟踪原件绑定受验版本。

`npm run snapshot` 为当前源码生成按内容摘要命名的 `evidence/source-manifest-<sha256>.json`，输出实际路径。已有目标以非零状态拒绝创建，包含相同源码重复执行的情况；核对后引用已存在的清单，不覆盖或重命名历史证据。排他创建不是崩溃时原子完整写入保证。

任何相关变更后，旧结果只证明旧版本，不能继续作为当前版本通过证据。只有重新验证或有依据地评估无关项，才能更新结论。审查后的修复和精简也在此列。失败、阻塞、跳过和未验证不得合并为通过。

工具链和命令只能从实际工程配置、锁文件与 CI 核对后添加。跨编译只证明构建范围；浏览器模拟只证明对应 Web 路径；实际原生窗口、安装包和真实设备的用户路径按目标平台分别验收。

## 本地愿景文件与忽略规则

完整最终愿景只存于根目录 `goal.md`，根目录 `.gitignore` 使用精确条目 `/goal.md`，不忽略其他目录的同名文件。公开文档应自含贡献所需的工程摘要，不复制私人愿景全文，不以缺少该文件阻止阅读。

`.gitignore` 只影响 Git 对未跟踪文件的默认处理，不是加密或访问控制，也不会使已跟踪文件自动退出索引。提交前核对实际索引与忽略匹配；已跟踪的私人内容须单独处理索引及历史暴露。

## 文档变更检查

- 阅读目标路径现状和未知修改后再编辑；文件读取失败不代表内容为空。
- 检查 UTF-8、末尾换行、尾随空格、Markdown 结构、相对链接与章节锚点。
- 对每个新文件可用 `git diff --no-index --check /dev/null <文件路径>` 检查空白；退出码 1 也可能只表示文件差异，应同时检查实际空白诊断。
- 检查确认目标、建议、假设、未决项和验证结果是否混写；不引用旧 Plums 结果作为新版证据。
- 对 `goal.md` 做本地链接检查，并单独检查去除该文件后的公开文档：仅指向它的已说明可选链接允许缺失，其他内部链接仍须完整。

工作流参考出处见 [README](../README.md#技术资料)。采用的是适合当前项目的工作约定，不复制其他项目的命令、自动发布流程或严重问题处理阈值。

## 本地交付目录

供本地查看的应用包统一放在仓库根 `release/`。此目录仅保存当前交付产物、精炼使用说明与校验清单，按 `/release/` 忽略并从源码盘点中排除；应用数据、缓存、原始日志、测试签名私钥及私人配置不进入交付目录。

Mac使用 `npm run release:mac` 统一构建普通debug包、本地临时签名、复制内容核对、文件校验及旧包归档；当前入口为 `release/mac/Plums M1.app`。同目录 build-info.json记录实际包标识、版本、架构、签名和文件校验，source.patch保存基线提交上的公开工作区差异；构建和签名通过不自动代表原生用户路径通过。Android当前包独立放在release/android，保留其受验来源，不因Mac更新而改写为同版验证。

需要先验收再交付时，执行 `npm run release:mac -- --stage`，读取命令输出的候选目录并在独立数据下启动其中的 app。通过验收和独立审查后，先关闭当前应用，再执行 `npm run release:mac -- --publish <候选目录>`，只移动这份受验包，不重新构建。省略参数直接构建并发布。候选与当前目录必须分开；发布保留整份旧平台目录，替换失败恢复旧入口并保留候选。此处是本地包替换，不是业务数据迁移或跨平台原子升级。

旧Mac交付按整个平台目录归入 `.cache/archive/releases/`，保留原包及来源；历史实验归入同一归档根下的压缩包。`.cache/archive/INDEX.json`记录已整理历史材料的路径与恢复方式；后续 `release:mac` 自动归档由命令输出和 releases 目录定位。恢复二进制前先关闭对应应用，使用隔离数据；恢复包不回滚应用数据。未知文件、在用模拟器、构建工具缓存和调试签名材料保持原位置，不通过清理中断当前操作。

当前操作和版本从README、HANDOFF及RESULTS查阅。阶段历史与失败证据保持原件；入口文档不复制多轮PID、临时脚本路径和交付时间线。项目清单、链接及隐私模式通过check:project检查，原始日志／截图继续忽略。

## 本地阶段提交

阶段提交先完成独立审查、必要修复、规范检查与重新验证。提交前逐项阅读精确暂存 diff 和全部待纳入文件，检查密钥、token、环境文件、真实数据、账号资料、私人路径、聊天或提示词记录及运行产物。允许使用可核验的 GitHub 用户名与 GitHub 邮箱，不据此纳入任意邮箱内容。

确认 `goal.md` 被忽略且未跟踪，不使用强制添加。身份使用可核验的现有 GitHub 身份，不改全局 Git 配置；无法确认时暂停提交。扫描只说明检查范围，不能证明不存在所有泄漏。不自动推送、部署或触发远端 CI。
