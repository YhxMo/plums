M1 实现与决策见 [实验记录](M1-EXPERIMENTS.md)，实际覆盖见 [证据](../evidence/RESULTS.md)。移动端验证从 M1 开始，不等桌面业务完成后再调查其可行性。M2、M3 的平台推进顺序在风险证据与设备条件明确后决定。

M4 的多 Agent 合作是工程目标明确的后期重中之重，人类理解角色卡是绝对重点；这不把产品愿景缩减为协作框架。M1–M2 只为通用通信、状态和参与者作用域留出空间，避免锁死单 Agent，不提前实现重型编排。

## M1 优先回答的问题

- 候选运行时在目标平台如何加载社区扩展？能否不依赖桌面 Node.js？原生编译时插件与动态扩展如何衔接？
- 服务依赖就绪、激活失败撤回、依赖替换与停用清理能否形成一致的最小契约？哪些约束依赖可信插件配合？
- 默认布局与导航能否通过相同公开契约被明显不同的 UI 替换，并在失败或停用后恢复？
- 状态持久化与迁移如何处理读取失败、中断、升级和恢复？前后台、系统回收、离线、长任务与文件授权如何表达？
- 候选通用组件的收益、许可证义务、依赖和移动端成本是什么？组件复用范围与代码依赖尚未确定。

每项实验先写通过与失败判据，再执行。只有编译成功不足以关闭生命周期、原生交互或移动端可用性问题。实验失败可以改变选型，不能改写成“平台已经支持”。

默认 UI 的参考界面在设计阶段核对，具体设计边界见 [架构文档](ARCHITECTURE.md#应用-ui-的扩展边界)；扩展可整体替换 UI。后期角色卡格式、A2A 适配及协作模型另行设计，尚未选标准或具体字段。

## 避免范围偏移

个人助理和 AI TRPG 可作为后续扩展实验，不构成先后必做产品路线。酒馆只可能是非主要、非官方扩展用途，不是角色卡的主要目标。历史能力检查只能补充回归，补齐既有缺口不构成最终完成标准。

遇到新需求时，先检查是否能通过现有扩展组合完成；确有通用缺口才演进契约，并增加可证伪实验。权限、资源、平台和兼容边界应保持明确，不因“开放扩展”承诺一切可用。
