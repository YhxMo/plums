# 性能基准

使用 `pnpm bench:performance` 对设置保存和能力调用做独立基准。命令先构建，再运行脚本；临时夹具位于系统临时目录，每个场景结束后清理。

```sh
pnpm bench:performance
pnpm bench:performance --out /tmp/plums-performance.json
```

`--out` 保存包含环境、场景、耗时、内存和查询计数的 JSON。它的父目录须已存在；运行报告不放进仓库。

## 方法

- 每个场景预热 5 次、采样 30 次，中位数和 P95 包含整个公开 API 调用。
- `setSettings` 使用 10、50、100 个整数设置项，每项的最大值不同；包含数据库读取、校验和设置文件写入。
- `runCapability` 使用 1、100、500 个包，每包 0、1、4 个密钥引用；额外覆盖 100 个包、每包 64 KiB payload 的场景。测量成功的 2.x egress 调用。
- 夹具准备在计时之外：设置包通过公开导入接口安装；能力场景批量写入合成安装元数据，再通过公开接口同意、启用和调用。
- 使用 `FakeModelProvider`、`MemorySecretStore`、`RecordingEgressSink` 和立即返回 true 的确认接口，审计回调为空；不打开网络。
- SQL 计数在预热后的单独调用中采集，分别统计 SELECT 的执行次数和所有 prepare 次数；语句复用不会被计成少执行查询。
- 采样前执行 GC，调用结束后读取 RSS、heapUsed、external，记录相对采样开始时的最大增量。这是观察到的采样增量，不能表示调用内部瞬时峰值；RSS 也受分配器保留页影响。
- 比较时固定机器、Node 版本和场景顺序，分别运行优化前后版本，避免与全量测试等负载同时运行。

## 确定性指标

| 成功调用                       | SELECT 执行次数 | 预热后的 prepare 次数 | SecretStore.get 次数     |
| ------------------------------ | --------------- | --------------------- | ------------------------ |
| setSettings（无密钥字段）      | 2 → 2           | 2 → 0                 | 0 → 0                    |
| runCapability egress，1 个包   | 25 → 20         | 25 → 0                | 每包 1 个引用时仍为 5    |
| runCapability egress，100 个包 | 520 → 20        | 520 → 0               | 每包 1 个引用时仍为 500  |
| runCapability egress，500 个包 | 2520 → 20       | 2520 → 0              | 每包 1 个引用时仍为 2500 |

成功的 fs read/list 调用在优化后执行 18 次 SELECT，write/exec/egress 执行 20 次，均与包数无关。密钥读取和脱敏工作仍随引用数量增长，每个审计时点继续刷新密钥值。

内部 SQL 缓存只复用固定语句，每次执行仍读取当前状态；关闭数据库时清空缓存。MCP 的动态 NOT IN 语句即时 prepare。设置验证器按有效约束内容复用，LRU 最多 256 项，单个 schema JSON 超过 16 KiB 时不缓存，Ajv 内部 schema 缓存会被清理。

## 验证

`pnpm test` 包含构建和全部回归测试。本次组合共 34 个测试文件、988 项检查通过，覆盖缓存淘汰和 schema 变更、密钥刷新与清理失败、数据库重开与迁移、同进程及跨进程状态变化、MCP 和 CLI 行为。

性能回归测试断言查询执行次数、语句复用和缓存边界；耗时与内存作为同机对比结果记录，不设置 CI 毫秒门槛。
